# 从零重建 Stock 完整实施设计

## 意图

从当前工作区重新建立 Stock/Aquila 的完整前后端和数据库实现，交付统一方案定义的单管理员本地资讯情绪闭环。目标是得到可从全新数据库安装、可测试、可恢复、可审计的模块化单体；当前工作区不含可直接沿用的应用实现。

## 当前状态与工作边界

- 用户选择在当前工作区实施新实现，不创建隔离 worktree。
- 用户明确选择从零重建，不恢复历史源码；工程目录可全新创建。
- 用户明确排除旧部署数据库：只新建独立 MySQL 8 数据库/schema，不检查、不迁移、不连接、不写入旧库。G01 对“历史工程/部署 schema”的盘点门禁据此申请标记 `N/A`，并在统一方案和登记表中记载该负责人的明确决定及范围；这不意味着其他门禁豁免。
- Copilot《统一落地实施方案》v1.4 是产品与技术基线；实施中保留 A–F 阶段及 G02–G05、覆盖/版本/清理等正确性门禁，并按本设计更新 G01 的适用范围。
- 规范来源固定为 `落地文档设计/Copilot/统一落地实施方案.md`（当前 v1.4）及 `落地文档设计/Copilot/运行与验收登记表.md`；§14 和登记表是验收/证据基线。开始实现前先按已批准的 G01 决定更新两份文件并升级基线版本；后续计划和实现均跟随最新经批准版本，历史设计文件不覆盖它们。
- 代码和全部业务迁移只面向明确创建的新数据库；生产来源、备份及发布继续受许可、设备和恢复证据约束。
- 用户选择按阶段门禁交付完整产品，并选择 Subagent-driven 执行。批准本设计后另编制完整实施计划及分阶段子计划；同一工作区中涉及共享 API/DDL 的改动按计划串行合并，不并行编辑相同文件。

## 目标

1. 建立 Java 17、Spring Boot 3、Vue 3、TypeScript、MySQL 8 的可重复开发/测试/构建基线。
2. 设计并实现完整业务 schema：身份/会话/恢复、自选/热门、证券主数据/导入、来源许可/任务/覆盖/raw、文档修订/提及/治理/job、情绪词典/结果/窗口/分析版本、告警/事件/静默/审计及维护/删除登记。
3. 通过版本化、可审查、可验证的 Flyway 迁移从独立空库建库；迁移账号与运行账号分离；所有事务、DDL 和索引在 MySQL 8 验证。
4. 完整实现统一方案中的单管理员资讯情绪闭环及前端工作台；生产来源、告警质量、备份和部署仅在对应门禁通过后启用。
5. 每项门禁和阶段退出条件都有责任人、实际证据、测试结果及可追溯结论。

## 非目标与失败条件

- 不恢复或搬运历史源文件，不把旧表结构/API 当作新实现事实；不接触旧部署数据库。
- 不在 G02 未通过时进行生产来源采集；不在 G04 未通过时启用正式备份或生产发布。
- 不引入微服务、消息中间件、外部模型、Docker/Compose，亦不在 V1 接入行情或交易执行。
- 不因赶工弱化覆盖完整性、任务恢复、修订防回退、撤权清理或版本原子切换要求。
- 若新代码意外覆盖历史内容、对旧数据库执行连接/读写、门禁缺少证据却标为通过，或测试证明关键数据正确性不成立，则停止相关实施并修复/重新评估。

## 考虑过的路径

1. **恢复历史实现后修补**：初期可能较快，但不符合用户要求从零开始；旧工程、迁移和环境状态未验证，容易误把历史假设当作当前事实。排除。
2. **先冻结全域 DDL，再一次性开发全栈**：前期能看到完整表关系，但会在来源/情绪细节未实测时锁定过多实现，且把集成风险推迟到最后。排除。
3. **从零重建完整产品，按 A–F 阶段和 Subagent-driven 子任务交付（选定）**：先建立工程与独立空库基线，再纵向实现各领域及对应迁移；每个阶段集成、测试和审查后才推进。用户确认旧库完全不在范围，故不执行 G01 旧工程/部署 schema 盘点；G02–G05 和其他正确性验收仍有效。

## 技术与数据设计原则

- 后端：Java 17 / Spring Boot 3；模块边界依统一方案；Controller → Application Use Case → Domain/Repository/Port；外部 I/O 和计算不在持锁事务中。
- 前端：Vue 3 / TypeScript；先建立类型化 API client、路由和明确加载/错误/空状态，最终由同源服务提供构建产物。
- API：`/api`、`Result<T>`、Cookie 服务端会话、CSRF/Origin 校验、统一分页和时间/ID 序列化；契约与 OpenAPI、DTO、测试同步。
- 数据库：MySQL 8、Flyway 版本化 SQL、显式约束/唯一键/索引和可重复空库构建。每个阶段增量迁移；先扩展、回填和校验，再切换读写；不修改已执行迁移，不假设 MySQL DDL 可事务回滚。
- 新库实体依统一方案的 `sys_* / m1_*…m8_*` 命名及领域关系演进；每一实体、列、保留期和索引须由实际查询/写入路径支撑。不得直接照抄历史迁移文件或用一张“总 DDL”越过阶段门禁。
- 覆盖、订阅生命周期、内容修订顺序、处理 fencing、输入变化日志、分析版本发布、告警和删除屏障按统一方案实现为可执行状态/事务规则，并以对应故障场景验收。
- 敏感配置不入库或日志；来源许可状态与来源运行状态分开；身份哈希/TOTP/恢复材料参数在对应阶段冻结并测试。

## 分阶段实施范围

### A — 新项目与数据库基线

1. 按用户决定将历史工程与部署 schema 标为范围外，在统一方案/登记表记录 G01 的 `N/A` 理由及批准人；不做旧库盘点。
2. 冻结目录/构建命令、配置与密钥边界、Clock/错误响应、OpenAPI、测试与迁移策略。
3. 建立全新后端/前端、同源 API/UI 健康旅程和 MySQL 8 独立空库。
4. 建立完整业务 schema 的逻辑关系/迁移路线图，并以最小真实业务纵向切片开始落地；业务表按 B–E 域拆分迁移，不造空占位表。
5. 完成空库安装、重复启动、集成测试基线；验证迁移用户与运行账号分离。
6. G03/G04 的设备与恢复验证作为环境允许时的并行证据；正式备份和生产发布保持关闭直至相应门禁通过。
7. 建立证据目录、复核工具版本与估算；不再要求执行 G01 旧系统盘点或使用登记表跑通 G01 演练。

### B — 身份与主数据

按统一方案实现单管理员初始化/登录/TOTP/恢复码/会话撤销、CSRF 与限速、证券主数据、自选/热门及两阶段导入导出。冻结安全参数并完成恢复旅程、授权、并发容量、幂等和迁移验证；所有表均由新迁移建立。

### C — 单源采集与治理

实现许可策略、Adapter 接口、raw 与修订、覆盖事实、持久游标/任务/fencing、规范化、去重、证券关联、质量和生命周期屏障。G02 获批前只使用合法 fixture，不访问真实来源；完成 FT-01/02/03 等场景；无法证明覆盖时不得声明 COMPLETE。

### D — 情绪与工作台

建立不可变词典/算法/聚合版本、逐文结果、dirty 窗口和可恢复回算；执行在线追平、有限发布屏障、验证与 CAS 激活。完成版本间对账、不混版查询和失败/回滚测试，冻结质量参数。

### E — 告警运营

按完整覆盖及样本门槛计算声量告警；实现事件证据、审计、静默、冷却、迟到修正、死信及受限重放。覆盖不完整必须显示暂停评估，不得表现为“无告警”；历史重放默认不发旧告警。

### F — 稳定发布

完成到期清理、日志指标、容量/持续运行、原生安装升级、正式备份恢复和目标平台验证。只有所选部署平台及全部适用门禁有证据时才可 READY；否则明确 RESTRICTED/BLOCKED。

## 验收方式

- A 阶段先跑构建、单元/集成测试、OpenAPI 校验、Flyway 独立空库与重复启动。
- 所有 DDL 在 MySQL 8 验证；H2 或 mock 不能代替迁移/事务集成验收。
- 每阶段逐项运行统一方案 §14 和登记表对应的测试；高风险路径包含故障注入、恢复操作、不变量及证据产物。
- 结论只根据实际输出和可引用证据，不根据设计完成、文件存在或 HTTP 200 推断通过。
- 所有 DDL 只运行于本次新建的隔离数据库；不执行旧库/生产迁移。正式采集、备份和发布仍须各自门禁通过。

## 留给实施者的选择

在不改变用户已选边界及统一方案的前提下，实施者可确定目录细节、测试库启动方式、迁移文件拆分、OpenAPI 工具、最小健康页样式和非业务基础设施实现。选型须记录且可替换，不得引入额外运行时依赖来绕过门禁。
