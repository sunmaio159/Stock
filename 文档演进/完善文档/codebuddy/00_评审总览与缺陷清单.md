# Aquila 设计方案 V1.1 — 第二轮独立评审与完善建议（总览）

> 评审对象：`完善文档/00-10` 全套定稿（V1.1）
> 评审方式：跨文档交叉一致性比对 + 可执行性推演（DDL 能否达到设计意图 / 契约能否支撑页面 / 计划能否覆盖交付物）
> 评审结论：**设计质量整体较高**（单事实源、勘误表、量化验收都已到位），但仍存在缺陷。
> 本轮发现的是**定稿之后仍然遗留**的问题，与 `10_评审与修订记录.md` 已修的 P0-1~P0-4 / E1-E17 / G1-G6 **不重复**。
>
> **两份评审合并后**：技术层缺陷（A/S/P/API/ALG/OPS）**5 项 P0 + 19 项 P1 + 18 项 P2**，
> 与 [Copilot 汇报版评审结论](../Copilot%20Free/汇报版评审结论.md) 交叉后**新增治理/架构类缺陷（C 类）10 项**，
> 合计 **P0 7 项 / P1 25 项 / P2 20 项 = 52 项**。详见 §四之二 与 §六之二。

## 一、总体判断

| 维度 | 评价 | 说明 |
|---|---|---|
| 文档治理 | ⭐⭐⭐⭐⭐ | 单事实源、仲裁规则、勘误表机制成熟，是本方案最强项 |
| 数据库设计 | ⭐⭐⭐☆ | 表齐全，但"分区表约束 + 幂等语义 + 用户维度"三处硬伤 |
| 架构与流水线 | ⭐⭐⭐⭐ | 线程模型与背压思路正确，但两处策略自相矛盾 |
| API 契约 | ⭐⭐⭐☆ | 读接口完备，**写接口与后台接口大面积缺失** |
| 算法口径 | ⭐⭐⭐☆ | 公式成型，但依赖了不存在的字段，且存在边界放大 |
| 范围基线与计划 | ⭐⭐⭐ | **行情数据源缺口**是最大范围漏洞，计划未覆盖后台/运维类任务 |

**一句话结论**：方案"能讲清楚"，但**按现状直接开发会在 W4（详情页 + 工作台）撞上"行情从哪来"的墙，并在 W6 上线前撞上"告警事件按用户查不动"和"Raw Lake 当天幂等失效"两堵墙**。这三件事必须在 W0 前定稿。

## 二、阻断级缺陷（P0，共 7 项，必须在 W0 前决策）

| 编号 | 缺陷 | 所在文档 | 后果 |
|---|---|---|---|
| **A-01** | **行情数据源缺口**：`01 §五` V1 明确不做行情采集，`03 §7` 的 `m6_quote_daily` 是 V2 预留，但 **5 处 V1 交付物强依赖实时/收盘行情** | 01/02/03/04/07/09 | 工作台、详情页速览、WS 行情推送、价格告警、大盘速览全部无米下锅 |
| **S-01** | `m8_alert_event` **无 `user_id` 字段**，却声明了名为 `idx_user_unread` 的索引 | 03 §6 | "我的告警"必须 JOIN 规则表，索引失效；越权校验无处落地 |
| **S-02** | `m3_raw_record` 唯一键 `(source_code, outer_id, fetched_at)` 中 `fetched_at` 精确到**秒**，与注释"当天内幂等由唯一键兜底"矛盾 | 03 §4 | 同帖当天二次采集必产生重复行，"幂等链第一级"失效 |
| **P-01** | 执行池用 `CallerRunsPolicy`，任务打满时**扫描单线程亲自执行任务**，与勘误 E1"扫描与执行分离"直接冲突（骨架代码里还注释"CallerRunsPolicy 下不抛"） | 05 §5.1 | 扫描被阻塞 30s+，全源调度停摆，正是 E1 要修的那个 bug |
| **P-02** | 治理队列背压采用"上游阻塞等待"，而阻塞发生在**持有 `sourceLock` 的采集线程**上，且无超时；同时两个队列共 2 万条驻留内存，宕机即丢、无补偿任务 | 05 §5.2 / 06 §1/§3 | 队列一满 → 该源长冻 → 逐步蔓延至采集全面停滞；宕机丢数据且对账才发现 |
| **C-01** | `m3_task_instance` **状态机不完整**（缺"待重试/已回放"）且**重放任务无法溯源**（无 `replay_of`） | 03 §4 | "可回放"在数据层不成立；回放与正常采集在同一张表里混在一起，无法区分与统计 |
| **C-02** | **审计能力为零**：无表、无接口、无埋点，词典修改/熔断重置/重放/规则变更均无留痕 | 03 / 04 / 07 | 数据突变无法解释"谁在什么时候改了什么"；汇报版列为治理 P0 |

## 三、重要缺陷（P1，技术类 19 项 + C 类 6 项 = 25 项，应在 W1–W3 内修完）

### 数据库（S 类）

| 编号 | 缺陷 | 影响 |
|---|---|---|
| S-03 | `m1_watchlist_item` 缺 `user_id`（仅 `group_id`） | 告警 scope 展开、"谁关注了这只股"反查需 JOIN，WS 订阅关系构建低效 |
| S-04 | `m4_entity_mention` 无时间字段、无级联清理；重放若用 `REPLACE INTO` 会换 `doc_id` 产生孤儿 | 90 天淘汰后 mention 残留膨胀；重放产生脏数据 |
| S-05 | `m8_alert_channel` 无归属（`uk_channel_name` 全局唯一） | 个人用户只能共用运营配置的机器人，无法自定义企微 webhook |
| S-06 | 备份策略与容量矛盾：核心表日备 ≈15GB，本地保留 7 天 ≈100GB ≫ 50GB 盘 | 备份必然撑爆磁盘或静默失败 |
| S-07 | 情感结果/情绪指数**无词典版本与算法版本** | 词典迭代效果无法评估、历史指数不可复现、无法 A/B |

### API 契约（API 类）

| 编号 | 缺陷 | 影响 |
|---|---|---|
| API-01 | **偏好设置 API 完全缺失**（有 `m1_user_preference` 表、有 `/settings/preferences` 页面、是 Must 项） | 前端无法落地 |
| API-02 | **词典管理 CRUD + CSV 导入 API 完全缺失**（`/admin/dictionary` 页面已列入 V1，04 §4 只有 crawl 类 ADMIN 接口） | 运营后台词典页无法落地 |
| API-03 | 数据源看板所需"24h 新增趋势""字段缺失率"无 API | 07 §6 看板无法落地 |
| API-04 | 写接口响应体未定义（`POST /api/watchlist/items`、`POST /api/alert-rules` 等均无响应示例） | 前后端各写各的，联调返工 |

### 算法口径（ALG 类）

| 编号 | 缺陷 | 影响 |
|---|---|---|
| ALG-01 | `w_account`（KOL/100）**依赖不存在的 KOL 数据**：无作者表、无 `kol_score` 字段 | 公式不可实现 |
| ALG-02 | `w_time = 0.5^(Δt/24h)`，收盘后发布的帖子 Δt<0 → **权重 >1 被放大** | 盘后帖绑架指数 |
| ALG-03 | `score=0`（未命中任何情感词）的样本以**全权重**参与加权，系统性把指数拉向 50 | 与"无数据 = NULL"的严谨语义自相矛盾 |
| ALG-04 | 板块指数"成分股按帖量加权"，但一帖可命中多只股票 | 板块 post_count 重复计数 |

### 架构 / 流水线（A / P 类）

| 编号 | 缺陷 | 影响 |
|---|---|---|
| A-02 | 告警评估为 **O(规则 × 标的) 全量扫描**（30s 一轮），无倒排索引、无指标缓存 | 规模稍涨即空转；声量类指标 30s 求值本就无意义 |
| A-03 | `m3_source_config.crawl_params` 存 `cookie/ua` **明文**，仅 webhook URL 声明加密 | 凭据泄露即等于账号被盗；无轮换机制 |
| P-03 | 重放链路边界未定义：`target=parse\|govern` 是否连带情感与指数重算？ | 06 §2 说"重放 30 天"，04 限制"窗口 ≤7 天"，口径打架 |
| P-04 | 部分成功场景记账错误：反爬中断时已有记录入库却记 `FAILED` | 对账 diff 虚高 |

### 运维 / 计划 / 测试（OPS 类）

| 编号 | 缺陷 | 影响 |
|---|---|---|
| OPS-01 | **短信验证码落地门槛未评估**：国内短信签名需企业资质 + 网站备案，个人主体基本申请不下来；成本也未计入 | 登录（V1 第 1 项交付物）可能根本发不出短信 |
| OPS-02 | **无历史数据冷启动回补**：详情页 `trend7d`、突增"上一交易日基线"上线即为空 | 首周核心体验不可用 |
| OPS-03 | 分区新增、DB buffer 回放、死信重试三项**均无落地任务与监控**（09 计划里找不到） | 分区不新增 → 数据全落 `p_max` → 淘汰时全量误删 |
| OPS-04 | 缺少安全测试：越权（A 访问 B 的自选/规则/事件）、SQL 注入、帖文标题 XSS | 多用户 + ADMIN 接口下风险实质存在 |
| OPS-05 | `limiters` 用 `computeIfAbsent` 缓存，后台改 `rate_limit_qps` 后**不生效** | 反爬调参需重启 |

## 四、优化项（P2，共 18 项，可排后端）

| 编号 | 缺陷 | 建议 |
|---|---|---|
| S-08 | `content_hash` 为 STORED 生成列但无索引无人用 | 删除，省 CPU 与存储 |
| S-09 | `idx_simhash`（B-tree）对汉明距离检索无效 | 删除或改作精确排重 |
| S-10 | `dedup_key varchar(80)` 构造规则与长度上限未定义 | 固定格式 + 单字段 ≤20 字符，或改用 `UNHEX(SHA1(...))` 定长 40 |
| S-11 | `m2_trade_calendar` 缺 `prev_open_date` | 加冗余列，突增与日频任务免子查询 |
| S-12 | `m5_sentiment_result` 90 天淘汰 vs `m5_sentiment_index` 永久保留 | 声明"90 天内可重算，超期仅保留结果" |
| S-13 | `m5_sentiment_index_15m` 无 `scope_type` | 补列，为 V2 板块突增留基线 |
| API-05 | "HTTP 恒 200" 与"限流返回 HTTP 429"自相矛盾 | 明确：429 为传输层例外 |
| API-06 | `nextCursor` 排序键与编码未定义 | 固定 `ORDER BY published_at DESC, id DESC` |
| API-07 | WS 消息无 `traceId` | 与 HTTP 一致透传，便于排障 |
| ALG-05 | `w_interaction = log(1+互动数)` 无上限 | clamp 到 `[0.5, 3]`，防单帖绑架 |
| OPS-06 | 优雅停机 30s 排空 2 万条过紧 | 提至 60s，且先停上游再排空 |
| OPS-07 | 无审计日志表（ADMIN 改词典/重置熔断/重放无留痕） | V1 加 `sys_audit_log`（最小版） |
| OPS-08 | 500 条标注集无标注规范与一致性指标 | 补充标注手册 + 双人 Kappa ≥0.7 |
| OPS-09 | 监控缺业务指标 | 补：NULL 指数占比、去重率、死信积压、帖均处理耗时 |
| OPS-10 | 夜间补发未再过降噪 | 08:00 补发时也走冷却/日上限 |
| OPS-11 | `Idempotency-Key` 存储结构与 TTL 未定义 | 明确 Redis key 与结果体大小上限 |
| A-04 | `m8_alert_rule.dsl` 无版本字段 | 加 `dsl_version`，白名单升级后可识别旧数据 |
| A-05 | 合规：付费商用 + 采集 UGC + 存储作者哈希 ID，ToS/PIPL 风险提示不足 | 06 §8 增加法务条目与"商用前评估"前置条件 |

## 六之二、与 Copilot 汇报版评审的对照与采纳

### 定位差异（两份评审不冲突，是互补的）

| | 本轮 codebuddy 评审 | Copilot 汇报版评审 |
|---|---|---|
| 视角 | 工程实现层（能否编译、能否跑通、能否查得动） | 治理与管理层（能否扩展、能否解释、能否控住） |
| 方法 | 跨文档交叉比对 + DDL/契约可执行性推演 | 结构性风险与成熟度判断 |
| 产出 | 53 项带编号缺陷 + 可粘贴的 DDL/代码/契约 | 5 大风险域 + 5 套完善方案 + 优先级建议 |
| 结论 | 有 7 项 P0 会直接卡住 W2/W4/W5 | "值得推进，但必须稳定优先、范围收敛、可观测性先行" |

**两者对最终判断一致**：方案可以进入开发，但**不能直接按现状全量开工**。

### 汇报版五大主题 → 本轮处置

| 汇报版主题 | 处置 | 具体落点 |
|---|---|---|
| 单机单实例与实时场景冲突 | **采纳，降级为 P1**（V1 单机是显式决策且规模 ≤100 人，不构成 P0；但演进接口必须留） | **C-07**（02 号文件新增演进接口预留清单） |
| 情绪指数可信度边界不足 | **采纳** | **C-03**（04 号文件新增"二级参考信号"定义）+ ALG-03 的 `sample_post_count` |
| 回放/版本/审计不完整 | **采纳，两项提为 P0** | **C-01 / C-02**（01 号文件补状态机与审计表）+ C-04（三类版本补齐）+ 已有 S-07 |
| 监控与质量门禁不够强 | **采纳** | **C-05**（05 号文件新增工程质量看板 + 双周门禁） |
| 单体大泥球 / 扩展性 | **部分采纳**（V2 才需拆，V1 只做接口抽象，不做物理拆分） | C-07 + 09 范围守门强化 |
| 先可观测性后功能 | **采纳为流程约束** | 05 号文件新增"工程门禁与流程" |

### 汇报版提出但**不予采纳/降级**的两项

1. **"单机部署是 P0 风险" → 降级为 P1。** 理由：01 §一 已声明 V1 服务 ≤100 注册 / DAU ≤30 / 50 并发设计，单机单实例是该规模下的**正确取舍**；真正的风险是"没有留演进口子"，已由 C-07 覆盖。
2. **"V2/V3 提前做服务拆分" → 不采纳。** 理由：与 01 §六 V4 规模化阶段冲突，提前拆分会显著抬高 6 周 MVP 的交付风险。C-07 只用**接口抽象**换取未来拆分成本，不引入任何分布式组件（与 01 §四 Won't 项一致）。

### 汇报版的流程建议（照单落到 05 号文件）

- **先可观测性，再做功能展示** —— W0 增加监控埋点先行的出口条件；
- **每两周一次工程门禁** —— 05 号文件新增门禁检查表（7 项量化指标）；
- **最小可验证版本迭代** —— 与 09 关键路径一致，无需改动；
- **禁加功能条款** —— 05 号文件新增"V1 禁做清单"，与 09"范围守门"互为表里。
