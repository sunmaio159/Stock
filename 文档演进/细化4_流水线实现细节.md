> **文档性质**：对四条流水线的工程级细化——线程模型、队列参数、异常处理矩阵、重试与幂等、监控指标、容量计算
> **对应伪代码**：分册 B §3.1-3.5，本文档补充其未覆盖的"生产运行细节"

## 1. 流水线一：采集流水线

### 1.1 线程与调度模型

```
ThreadPoolTaskScheduler (poolSize=8)
├── 每源一把防重入锁: AtomicBoolean per sourceCode
├── 任务执行包装: 统一 try/catch → m3_task_instance 记账 → 指标上报
└── 拒绝策略: CallerRunsPolicy(采集任务可丢弃下一周期补,但需记 skipped 指标)
```

- 任务触发优先级：东财股吧（5min) > 雪球（10min) > 同花顺（15min)；线程满时低频源可跳过本轮
- **游标更新事务**：`last_cursor` 仅在"本批全部处理成功"后更新；部分失败则记录断点子游标，下轮从断点续采，保证 at-least-once

### 1.2 异常处理矩阵

| 异常 | 检测 | 处理 | 恢复 |
|---|---|---|---|
| HTTP 超时/5xx | HttpClient 捕获 | 失败计数+1；重试 ≤3 次（退避 1s/2s/4s） | 连续 5 次任务级失败 → 熔断开路 30s → 半开探测 |
| HTTP 403/验证码页 | 响应体特征匹配 | 立即熔断（不等5次）+ P0 告警运营 | 运营更新 UA/Cookie 参数后手动半开 |
| 解析异常 | Adapter.parse 抛错 | 该条 RawRecord 照存，parse 结果标记失败；任务记 partial_success | 修复 Adapter 后用 API10 重放 |
| P1 字段漂移 | SchemaValidator | 阻断该批入库 + 写 m3_drift_log + 告警 | 修复→重放 30 天 Raw Lake |
| 磁盘/DB 写失败 | SQLException | 重试 3 次，失败整批入本地降级文件（磁盘 buffer），DB 恢复后回放 | 启动时扫描 buffer 目录 |

### 1.3 幂等设计

- 键：`source_code + outer_id`；写入 `INSERT ... ON DUPLICATE KEY UPDATE raw_content=VALUES(...), interaction_count=VALUES(...)`
- 下游传递幂等键：RawRecord.id → NormalizedDoc 通过 `uk_source_outer` 二次幂等 → SentimentResult 通过 `uk_doc_engine` 三次幂等
- **重试安全结论**：整条链路任意环节重放/重试均不产生重复业务数据

### 1.4 容量与配置

- 东财股吧：~5400 标的 × 每帖列表页 20 条；按热度只采活跃吧（日有发帖的 ~2000 吧），每轮 ~2000 请求 / 5min → 平均 ~7 QPS，限流配置 5 QPS + 优先级队列
- 单帖处理预算：fetch ≤ 3s，parse ≤ 200ms，落库 ≤ 100ms → 单轮 ≤ 15min 内完成（留一倍余量）

## 2. 流水线二：治理流水线

### 2.1 队列拓扑（进程内）

```
rawQueue(10000) → CleanWorker(线程2) → cleanQueue(10000) → DedupWorker(线程2)
→ dedupQueue(10000) → EntityWorker(线程4,CPU密集) → entityQueue(10000)
→ QualityWorker(线程2) → sinkQueue → IndexSink(批量200条/或500ms flush)
```

- 队列满 → 采集线程阻塞（背压向上游传导），并上报 `queue.full` 指标告警
- 单 Worker 处理异常：该条重试 3 次 → 仍失败写 `m4_dead_letter(stage, payload, error_msg)`，**不阻塞后续消息**

### 2.2 各 Worker 关键实现决策

| Worker | 决策 | 理由 |
|---|---|---|
| Clean | 广告正则集入库（m5_sentiment_dict 同款字典表机制，type=6），热更新 | 广告话术演变快，不能发版 |
| Dedup | SimHash64 计算后，与 Redis 中该标的近 24h simhash 集合比对（汉明 ≤3 用分桶索引：按高 16 位分桶，桶内逐一比对） | 全量比对 O(n) 不可行；分桶后桶内 <100 条 |
| Entity | AC 自动机词典 = m2_security.name + m2_security_alias（简称/俗名）；**多实体冲突时取提及次数最多者为主标的**，全部实体写 m4_entity_mention | 一帖多股场景常见 |
| Quality | 规则分：字数 <10 → -2；含广告词 → -3；作者日产出 >50 帖 → 水军候选；互动数高 → +1；clamp 到 [1,5] | 纯规则起步，可解释 |

### 2.3 对账指标（每日 02:00 批任务）

```
采集条数 = 治理输入 = (正常产出) + (去重标记) + (无实体丢弃) + (死信)
四层数字不一致 > 0.1% → 告警 + 自动生成对账差异报告
```

## 3. 流水线三：情感流水线

### 3.1 L1 规则引擎实现要点

```
score_raw = Σ(情感词权重 × 程度副词系数 × 否定翻转(-1)^n × 转折规则)
score = tanh(score_raw / 3)          # 压缩到 (-1,1)
label = score>0.2 ? positive : score<-0.2 ? negative : neutral
confidence = min(1, 命中词数/3) × (1 - 否定歧义惩罚)
```

- 词典加载：启动全量加载 + 后台修改后 Redis pub 通知热加载（版本号校验）
- 转折句规则：检测到"但是/不过/然而"后，逗号分句，**后半句权重 ×1.5，前半句 ×0.5**

### 3.2 指数计算调度

| 任务 | 频率 | 输入 | 输出 |
|---|---|---|---|
| 15min 滚动 | 每 15min（交易日 9:00-15:30 + 盘外每 30min） | 窗口内 SentimentResult | m5_sentiment_index_15m + Redis 最新值 |
| 日频终值 | 每交易日 17:00（预留 1h 数据收尾） | 当日全量 | m5_sentiment_index（UPSERT uk_code_date） |
| 板块指数 | 日频 17:10 | 成分股指数 × 帖子数加权 | 同表（scope 区分） |
| 补算 | 治理重放后触发 | 受影响 code+date 集合 | 上述两表对应行重算 |

- **重放联动**：API10 重放完成 → 产出受影响 (code, tradeDate) 清单 → 触发指数补算 → 刷新 Redis

### 3.3 突增检测（V1 简版 → V2 完整）

| 模型 | V1 | V2 |
|---|---|---|
| 环比突增 | ✅ 当日累计 > 昨日同期×3 且 >30 帖 | ✅ |
| Z-Score | ❌（需 20 日基线积累） | ✅ Z>3 |
| 情绪反转 | ❌（需 15min 指数稳定运行 2 周） | ✅ 1h 跌幅 >40% |

V1 已在 W4 落 15min 派生表，正是为 V2 积累基线数据——**这是 V1→V2 的隐性关键依赖**。

## 4. 流水线四：投研流水线（V1 范围）

V1 仅覆盖"情绪因子 → 详情页舆情卡片"段；因子引擎/评分卡 V2/V3。V1 必须固化的两点：

1. **因子输入快照约定**：任何评分/指数落库时必须同时存输入快照（`weight_detail` / `factor_snapshot`），否则"当时 vs 现在"对比无从谈起
2. **详情页聚合的并发模型**：七卡片并行 CompletableFuture（每卡片独立超时 500ms，超时返回 `{available:false}`），聚合总预算 700ms

## 5. 统一监控指标（Micrometer → Actuator `/actuator/prometheus` 格式）

| 指标 | 类型 | 标签 | 告警阈值 |
|---|---|---|---|
| `crawl_task_total` | Counter | source, status | 单源 1h 成功率 <99% |
| `crawl_task_duration` | Timer | source | P95 > 基线×2 |
| `crawl_circuit_state` | Gauge | source | 开路 >5min |
| `pipeline_queue_size` | Gauge | queue | >8000 持续 10min |
| `govern_dead_letter_total` | Counter | stage | 1h 增量 >100 |
| `sentiment_index_lag` | Gauge | — | 日频 18:00 未完成 |
| `alert_push_fail_total` | Counter | channel | 1h >5 |
| `reconcile_diff_ratio` | Gauge | layer | >0.1% |

**日志规范**：全链路 traceId 透传（采集任务生成 → 治理 → 情感 → 告警同一 traceId），MDC 注入；任何 WARN 以上日志必带 `sourceCode`/`securityCode` 上下文。

## 6. 故障演练清单（W6 任务 6.4 的执行细节）

| # | 故障注入 | 预期表现 | 验收 |
|:-:|---|---|---|
| 1 | 东财源返回 403 | 立即熔断 + P0 告警 + 雪球/同花顺继续 | 告警 ≤1min 到达企微 |
| 2 | kill Redis | 工作台/详情页降级回源 MySQL（P95 允许升至 2s）+ 告警 | 无 5xx 雪崩 |
| 3 | kill MySQL 30s | 采集落盘 buffer，恢复后自动回放，无数据丢失 | 对账 diff=0 |
| 4 | 治理队列灌满 | 背压阻塞采集 + queue.full 告警，不丢消息不 OOM | 恢复后自动消化 |
| 5 | 企微 webhook 失效 | push_status=2，站内信兜底仍可达 | 事件不丢 |

## 7. 配置中心（application.yml 关键项汇总）

```yaml
aquila:
  crawl:
    thread-pool-size: 8
    circuit: { fail-threshold: 5, open-seconds: 30 }
    retry:   { max: 3, backoff: [1000, 2000, 4000] }
  govern:
    queue-capacity: 10000
    batch-flush:    { size: 200, interval-ms: 500 }
    simhash:        { hamming-threshold: 3, window-hours: 24 }
  sentiment:
    l1: { pos-threshold: 0.2, neg-threshold: -0.2 }
    index: { daily-cron: "0 0 17 * * MON-FRI", rolling-15m-cron: "0 */15 9-15 * * MON-FRI" }
  alert:
    default-cooldown-seconds: 900
    default-max-per-day: 10
```

> 词典、广告正则、源策略等**业务参数一律入库 + Redis 热加载**，yml 只放工程参数——这是"调权重不发版"原则在配置层的体现。
