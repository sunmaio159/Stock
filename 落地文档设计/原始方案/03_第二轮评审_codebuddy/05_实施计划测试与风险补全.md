## 三、OPS-01 短信验证码落地门槛（重要，易被忽略）

### 问题

`01 §五` 第 1 项交付物是"手机号 + 验证码登录"，但：

1. **资质门槛**：国内短信服务（阿里云/腾讯云）申请短信签名需**企业营业执照 + 网站 ICP 备案**，个人主体基本无法通过；审核周期 1-3 个工作日（企业）或无法通过（个人）；
2. **成本未计入**：`08 §4` 成本表只有云主机/RDS/Redis/数据源/域名，**没有短信费用**（≈¥0.04/条，按 100 用户 × 30 次/月 = ¥120/月，占预算 12%）；
3. 无"验证码发送失败"的降级路径。

### 建议方案（三选一，推荐 A + C 组合）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐主）** | 保留短信，但**同时提供邮箱验证码**（无资质门槛，成本≈0） | 双通道，注册时可选；短信不可用时系统不掉线 |
| **B** | 邀请码 / 管理员开通账号 + 密码登录（BCrypt，表已支持 `password_hash`） | V1 用户 ≤100 且多为自用/小团队，最简单可靠 |
| **C（推荐辅）** | 开发环境固定验证码（`profile=dev` 时返回 code，不上真实通道） | 降低开发期成本与依赖 |

**修订落点**：
- `01 §五` #1 改为"登录（**手机号验证码 / 邮箱验证码 双通道**，JWT AT 2h / RT 7d）"；
- `03 §2` `sys_user` 增加 `email varchar(64)` + `uk_email`；`sys_sms_code` 改名语义扩展为 `scene='login_sms'|'login_email'`，或新增 `sys_email_code`；
- `08 §4` 成本表补"短信 ¥120/月（邮箱通道为 0）"，总成本仍 ≤¥2 万/年；
- `08 §3` 风险清单新增 **R10：短信通道不可用**（🟡，应对：邮箱验证码 + 邀请码兜底）。

## 四、OPS-02 冷启动数据回补

### 问题

V1 上线首日：
- 详情页 `trend7d`（近 7 日情绪趋势）为空；
- 突增检测"当日累计 > 上一交易日同期 ×3"无基线 → 首日必然不触发（或误触发）；
- 工作台"情绪红黑榜""市场情绪温度计"全空。

### 方案

1. **上线前回补**：W4 增加任务 4.6，用采集器对三源做一次**历史回补**（东财股吧/雪球按时间倒序可翻页，回补 10-30 天；注意遵守 QPS 自律，建议放在非交易时段低峰跑）；
2. **UI 容错**：回补未完成前，`trend7d` 展示"数据积累中（已收集 N/7 天）"，突增卡片展示"基线建立中（需 2 个交易日）"——**不要显示 0 或 50**；
3. **基线就绪判定**：`m5_sentiment_index_15m` 满 20 个交易日同槽样本后才开启 Z-Score（V2），V1 环比模型只需 1 个上一交易日。

## 五之二、工程质量看板与双周门禁（C-05）

> 来源：汇报版评审 §三.4 / §六方案二.5 / §七.2 —— "文档里提到监控，但还没做到可量化的质量治理"。

### 1. 工程质量看板（9 项，V1 上线前必须可查）

| # | 指标 | 计算口径 | 门禁阈值 | 数据来源 |
|:-:|---|---|---|---|
| 1 | 采集成功率 | 成功任务 / 总任务（1h 滑窗，按源） | ≥99% | `crawl_task_total` |
| 2 | **任务重试率** | `retry_count>0` 任务 / 总任务 | ≤3%（超则查源稳定性） | `m3_task_instance` |
| 3 | **死信率** | 死信条数 / 治理产出 | ≤0.5% | `govern_dead_letter_total` |
| 4 | **去重命中率** | `is_duplicate=1` / 治理总数 | **5%~40% 为健康区间**，越界告警（过低=去重失效，过高=源重复灌水） | `m4_normalized_doc` |
| 5 | **去重误判率** | 周度人工抽检 200 条 | ≤5% | 抽检记录（`m5_label_set` 旁挂） |
| 6 | **词典更新覆盖率 / 回归** | 标注集回归准确率环比 | **下降 ≤3pp**（超出阻断发布） | `m5_label_item` |
| 7 | **告警噪音率** | `ack_status=2(已忽略)` / 总事件 | ≤30%（超则收紧默认阈值） | `m8_alert_event` |
| 8 | 热帖延迟 P95 | 发布 → 可见 | ≤3min | 埋点 + 08 §2 |
| 9 | **详情页异常卡片率** | `available:false` / 卡片请求总数（**仅统计 overview+sentiment**，V1 五张占位卡不计） | ≤0.5% | 前端埋点 |

> 其中 **2/3/4/5/6/7/9 为汇报版指出但原方案缺失的 7 项**，本轮全部补齐。

### 2. 双周工程门禁（每两周一次，未过则当周不加新功能）

| 检查点 | 通过标准 |
|---|---|
| 采集成功率 | 三源 72h ≥99% |
| 词典回归 | 准确率不低于上一版 −3pp |
| 去重质量 | 命中率在区间内 + 误判率 ≤5% |
| 详情页 P95 | ≤800ms（50 并发） |
| 告警噪音率 | ≤30% |
| 任务回放 | 抽一次源，重放 7 天窗口成功且指数重算一致 |
| 死信与对账 | 死信清空、四层对账 diff ≤0.1% |

### 3. 流程约束（汇报版 §七，直接采纳）

**（1）可观测性优先于功能展示**
W0 出口条件追加：**监控埋点先行** —— `crawl_task_total` / `pipeline_queue_size` / `api_latency` 三个指标在 W1 结束前必须可见，否则不允许进入 W2 功能开发。

**（2）"禁加功能条款"——每次需求评审必问三句**
1. 这个功能在 V1 是否必要？
2. 如果不做，会不会影响核心价值（情绪 + 告警 + 信息筛选三合一）？

**（3）V1 禁做清单（与 09"范围守门"互为表里，冲突时以此为准）**
