## A-01（P0）行情数据源缺口 —— 本轮最重要发现

### 问题描述

`01 §五` V1 明确不做行情采集（`m6_quote_daily` 是 V2 预留），但 V1 交付物中**至少 5 处强依赖行情数据**：

| 依赖点 | 文档位置 | 需要的行情 |
|---|---|---|
| 工作台自选股列表 `price` / `changePercent` | 04 §2 | 实时快照 |
| 大盘速览：三大指数 + **涨跌家数** | 07 §3 卡片 2 | 指数实时 + 全市场统计 |
| 详情页速览卡 `price` / `changePercent` | 04 §6 | 实时快照 |
| WebSocket `/user/queue/quote` 3-5s 推送 | 04 §8 | 实时快照 |
| 告警指标白名单 `price`（op `>=`/`<=`） | 04 §7 | 实时快照 |
| 工作台 `marketSnapshot` | 04 §2 | 指数实时 |

同时 `02 §一` 的层间铁律又声明"行情数据**不走**治理流水线，落 `m6_quote_daily` 等专用表（V2）"——即 V1 既没有行情采集、也没有行情表。结果是 **V1 的 14 项交付物中至少 4 项在 W4 会直接卡死**。

### 三个可选方案

| 方案 | 做法 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| **A（推荐）** | V1 增加"**行情快照采集**"：用东财 `push2` / 腾讯 `qt.gtimg.cn` 等公开行情接口，**批量拉取**（一次请求可带数十只股票），仅采 ①自选股 ②三大指数 ③全市场涨跌家数 | 极低（QPS 可控制在 1-2/3s，机器成本不变） | 接口非官方、可能变更；但只取快照、量小、有降级 | **采纳** |
| B | V1 行情降级：全站只展示**上一交易日收盘价**，UI 明确标注"延时行情"，价格告警改为收盘价触发 | 零 | 工作台"实时监控"场景（01 §二 场景 2）名存实亡 | 仅在 A 不可行时采用 |
| C | 接付费行情 API | ¥500-3000/月 | 与"年成本 ≤2 万"冲突 | 不采纳 |

### 方案 A 落地设计（建议直接并入 02/03/04/09）

**1）架构定位**：属于**采集层**，但**直通应用层**，不进治理流水线（符合现有层间铁律）。

```
QuoteSnapshotScheduler(交易日 09:25-15:05, 每 3s)
   → 批量拉取: 全部被关注标的(SecurityCodeSet = 自选股∪告警scope∪指数)
   → 写 Redis quote:snapshot:{code} (TTL 30s)  +  market:summary:{date} (TTL 5min)
   → 收盘 15:05 落 DB m6_quote_daily(提前启用 03 §7 预留表) 一份
   → 非交易日: 每 5min 拉一次(维持指数展示) 或直接使用最后收盘价
```

**2）关键设计点**：
- **按需采集，不做全市场**：标的集合 = `SELECT DISTINCT security_code FROM m1_watchlist_item UNION 告警 scope 展开 UNION 三大指数`。V1 规模下该集合 ≤ 数千，去重后实际通常 < 500；
- **批量接口**：单次 HTTP 带 50-100 个代码，3s 一轮 → 实际 QPS ≈ 0.3-1，远低于现有 5 QPS 自律上限；
- **与告警/WS 解耦**：行情快照写 Redis，WS 推送线程从 Redis 读（而非各自拉源），避免 N 个用户 N 倍请求；
- **降级**：行情源失败 → `marketSnapshot=null` + 响应头 `X-Degraded: quote`（04 已定义），价格告警暂不评估并记 `alert_quote_stale` 指标；
- **熔断/限流/记账复用** `m3_source_config`（新增 `source_type=5` 行情源，复用三态熔断）；
- **成本**：无新增费用；`01 §五` 新增第 15 项交付物"实时行情快照"。

**3）需连锁修订的文档**：
- `01 §四 MoSCoW`：新增 Must 项"实时行情快照采集（公开行情接口，仅自选+指数+涨跌家数）"；§五 新增交付物 #15；§六 V2 中"行情日K采集"改为"历史日K与分钟K"；
- `02 §一`：数据源层加"公开行情接口(V1 快照)"，应用层加"行情快照";§二 Redis Key 表补 `market:summary:{date}`；
- `03`：**提前启用** `m6_quote_daily`（V1 仅收盘一份，不分区即可）；
- `04 §2/§6/§8`：价格字段来源明确为"行情快照，非交易时段为最近收盘价"，并补 `stale` 标识字段；
- `07 §3`：大盘卡"涨跌家数"数据源确认可用；
- `09`：W1 新增 `1.8 行情快照 Adapter`；W4 `4.3` 由"简版"升级为正式实现。

## P-01（P0）`CallerRunsPolicy` 破坏"扫描与执行分离"

### 问题描述

`05 §5.1` 勘误 E1 的核心修复就是"扫描与执行分离，杜绝饿死"。但骨架代码选用了 `ThreadPoolExecutor(8, CallerRunsPolicy)`：

- 当 8 个执行线程全部被占用时，`CallerRunsPolicy` 会让**提交方（即唯一的扫描线程）自己执行任务**；
- 采集任务耗时通常是秒级到 30s 级 → **扫描线程被占用 → 30s 扫描周期被拉长到分钟级 → 全源调度停摆**；
- 这恰恰是 E1 要消灭的那个 bug，**修复引入了新的同类缺陷**；
- 骨架里还写了 `catch (RejectedExecutionException e)` 并注释"CallerRunsPolicy 下不抛，防御性处理"——说明作者已意识到二者互斥，但没回头改策略。

### 修正方案（推荐 A）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `AbortPolicy` + 有界队列（64）+ 扫描线程 `catch RejectedExecutionException` → 记 `crawl_task_skipped` 指标 + 下个扫描周期重试 | 扫描永远 30s 准时，背压可观测，符合"扫描不干活"原则 |
| B | `CallerBlocksPolicy`（自定义：提交线程阻塞等待槽位） | 会阻塞扫描，退化为 P-02 同类问题，不采纳 |

```java
// 修正后骨架（替换 05 §5.1）
private final ThreadPoolExecutor execPool = new ThreadPoolExecutor(
        8, 8, 0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<>(64),
        new ThreadFactoryBuilder().setNameFormat("crawl-exec-%d").build(),
        new ThreadPoolExecutor.AbortPolicy());       // 关键：不用 CallerRunsPolicy

void scanAndDispatch() {
    if (!running.get()) return;
    for (SourceConfig src : sourceConfigService.selectDue(LocalDateTime.now())) {
        AtomicBoolean lock = sourceLocks.computeIfAbsent(src.getSourceCode(), k -> new AtomicBoolean());
        if (!lock.compareAndSet(false, true)) continue;              // 上一轮未跑完，跳过
        try {
            execPool.execute(() -> { try { executeWithGuard(src); } finally { lock.set(false); } });
        } catch (RejectedExecutionException e) {
            lock.set(false);                                          // 释放锁，下轮再试
            Metrics.counter("crawl_task_skipped", "source", src.getSourceCode()).increment();
            log.warn("crawl exec pool full, skip sourceCode={}", src.getSourceCode());
        }
    }
}
```

**配套监控**：`crawl_task_skipped_total` 持续增长 > 10 分钟 → 告警（说明执行池长期打满，需要扩容或降频）。

**修订落点**：`05 §5.1` 骨架 + 新增勘误 **E18**；`02 §二` 调度行改为"扫描单线程 + `ThreadPoolExecutor(8, AbortPolicy)` + 有界队列 64"。

## P-02（P0）背压策略导致采集停滞 + 内存消息丢失无补偿

### 问题描述

`05 §5.2` / `06 §1` 规定：治理队列满 → "上游阻塞重试 + 告警"。

但这里的"上游"是**持有 `sourceLock` 的采集执行线程**：

```
采集线程(持锁) → governQueue.put() 阻塞 → sourceLock 一直不释放
   → 扫描每 30s 发现该源仍上锁 → 跳过 → 该源永久停止采集(直到队列消化)
   → 8 个执行线程逐个被阻塞 → 采集全面停滞
```

同时两个 `LinkedBlockingQueue(10000)` 是**纯内存**：进程 crash / 优雅停机超时 / OOM → 最多 2 万条已入库（`m3_raw_record`）但 `parse_status=0` 的文档**静默丢失**，只能靠每日 02:00 对账发现（滞后 1 天）。而 `06 §3` 声称"任意环节重试不产生重复业务数据"——**不重复 ≠ 不丢失**，这里 missing 了"不丢失"的承诺。

### 修正方案（三条一起落地）

**（1）背压改为"限时阻塞 + 释放锁 + 补投"**

```java
// 采集线程投递治理队列：限时 3s，超时则记 pending 并释放锁
boolean ok = governQueue.offer(doc, 3, TimeUnit.SECONDS);
if (!ok) {
    Metrics.counter("pipeline_offer_timeout", "queue", "govern").increment();
    pendingBacklog.add(doc.getRawRecordId());      // 只记 raw_record_id，不记对象（避免 OOM）
    // 注意：不抛异常、不阻塞；本轮视为"采集成功但治理延迟"
}
```

- `pendingBacklog` 为持久化的待补投清单（写 Redis `pipeline:pending:govern` 集合，或复用 `m3_raw_record.parse_status=0`）；
- 新增 `BacklogReplayer`：每 60s 扫描待补投清单，队列水位 < 50% 时按 `parse_status=0` 重新 `parse → 投递`；
- 采集任务**照常提交游标**（因为 raw 已入库，治理可异步补），避免"因下游拥堵而反复重采同一批"。

**（2）以 `m3_raw_record.parse_status` 为补偿事实源（消除内存丢失）**

`03` 中该字段已存在（0 待解析 / 1 已解析 / 2 失败），但**全系统没有任何任务消费它**。补全：

```
应用启动 / 每 5min 定时：
  SELECT id FROM m3_raw_record WHERE parse_status = 0 AND fetched_date >= CURDATE() - 1
  LIMIT 500 → 重新 parse → 投治理队列
治理成功后：UPDATE m3_raw_record SET parse_status = 1 WHERE id = ?
```

这样"内存队列丢消息"从**不可恢复**变成**最多延迟 5 分钟自动恢复**，`06 §3` 可以真正改写为"**不重复、且至多延迟补投、不丢失**"。

**（3）队列水位分级（替代"满了才告警"）**

| 水位 | 动作 |
|---|---|
| < 50% | 正常 |
| 50% - 80% | 记 `pipeline_queue_size`，无动作 |
| > 80% | WARN 日志 + `pipeline_queue_high` 指标，采集端开始记录 pending |
| = 100% | P1 告警 + 上游停止投递（限时 3s 超时即 pending，绝不无限阻塞） |

**修订落点**：`05 §5.2` 要点 1、`06 §1` 队列满策略、`06 §3` 幂等链补充说明、`06 §5` 新增指标 `pipeline_offer_timeout_total` / `pipeline_pending_size`。

## A-02（P1）告警评估改为倒排索引，并按指标周期分组

### 问题

`05 §5.5`：每 30s 扫描启用规则 → 按 scope 展开标的 → 求值。复杂度 O(规则 × 标的)，且**声量类指标（依赖上一交易日基线）每 30s 求值毫无意义**——30s 内基线根本不变，纯空转。

### 修正

**1）构建规则倒排索引（Redis，规则变更时重建）**

```
rules:by:security:{code}  → [ruleId...]     标的 → 关注它的规则
rules:by:watchlist:{gid}  → [ruleId...]
rules:by:metric:{metric}  → [ruleId...]     按指标类型分桶
```

**2）按指标自然周期分组调度**

| 指标 | 评估周期 | 说明 |
|---|---|---|
| `price` | 30s（盘中） | 依赖行情快照 |
| `sentiment_index` | 15min | 与 15min 派生表同频 |
| `volume_ratio`（声量环比） | 15min | 与 15min 派生表同频，V1 日频基线可降为 60min |

**3）指标值先算后匹配**：对每个**被关注的标的**（去重后通常 < 500）算一次指标，再广播给订阅它的规则 —— 复杂度从 O(R×S) 降为 O(S + 命中)。

**修订落点**：`05 §5.5` V1 实现范围第 1 条；`06 §1` 线程全景中 `alertEvalPool(2, 30s)` 改为"30s 价格组 + 15min 派生组"。

## P-03（P1）重放链路边界定义

### 问题

- `04 §4` `POST /api/crawl/tasks/replay` 的 `target` 只有 `parse` / `govern`，情感与指数是否被连带重算**未定义**；
- `05 §5.3.3` 说"重放联动 → 重算指数"，与 `target` 语义冲突；
- 窗口口径打架：`04` 规定 ≤7 天（4004），`06 §2` 写"重放 30 天 Raw Lake"，`01 §五` #13 写"Raw Lake 30 天重放"。

### 修正定义（写入 04 §4 + 06 §2）

1. **窗口口径统一**：Raw Lake **保留** 30 天；但**单次重放窗口 ≤ 7 天**（4004 保留），超过 7 天请分多次提交。`01 §五` #13 文案改为"**Raw Lake 30 天可重放（单次 ≤7 天）**"；
2. **重放是整条下游链路的级联**，不是单段：

```
replay(sourceCode, start, end, target)
  target=parse   →  重新 parse raw → 重新治理 → 重新情感 → 重算受影响(code, tradeDate)指数 → 刷缓存
  target=govern  →  跳过 parse，直接用已解析结果重跑治理 → 后续同上
  V1 不提供单独"只重算指数"入口（需要时走 target=govern 即可覆盖）
```

3. **重放必须产出差异报告**：`{total, done, failed, indexRecalculated:{(code,date)[]}, sentimentDiff:{changed, unchanged}}`，供运营确认；
4. **同源互斥**（4005）保留；跨源可并行，但指数重算需串行（避免同 `(code,date)` 并发 UPSERT）。

### 附带修复：P-04 部分成功记账

`05 §5.1` 中 `AntiCrawlException` 分支直接记 `FAILED`，但该批次可能已 upsert 了部分记录。修正：

```java
} catch (AntiCrawlException e) {
    circuitBreaker.openImmediately(src);
    alertService.p0("源被反爬: " + src.getSourceCode());
    taskService.finish(run, result != null && result.recordCount() > 0 ? "PARTIAL" : "FAILED",
                       result == null ? 0 : result.recordCount(), e.getMessage());
}
```

## OPS-05（P1）RateLimiter 热更新不生效

`05 §5.1` 用 `limiters.computeIfAbsent(code, k -> RateLimiter.create(qps))` 缓存实例，运营后台改 `m3_source_config.rate_limit_qps` 后**永不生效**（需重启）。反爬应急调参恰恰最需要热生效（R1 风险应对手段之一）。

```java
// 监听源配置变更（DB 轮询 30s 或 Redis pub），变更时重建
public void onSourceConfigChanged(SourceConfig src) {
    limiters.put(src.getSourceCode(), RateLimiter.create(src.getRateLimitQps()));
}

// 或惰性校验：每次取用时比对期望 QPS
private RateLimiter limiter(SourceConfig src) {
    RateLimiter l = limiters.get(src.getSourceCode());
    double expect = src.getRateLimitQps();
    if (l == null || Double.compare(l.getRate(), expect) != 0) {
        l = RateLimiter.create(expect);
        limiters.put(src.getSourceCode(), l);
    }
    return l;
}
```

同时把 `rate_limit_qps` 纳入 05 §6"业务参数入库 + 热加载"清单（`06 §9` yml 注释里已声明该原则，此处只是补齐实现）。

## OPS-06（P2）优雅停机窗口

`06 §1`："停止扫描 → 队列排空（≤30s）"。两队列最多 2 万条，30s 需 667 条/s，治理单条事务（写 doc + mention）在 HDD/小规格 RDS 上难保证。建议：

- 停机顺序改为：停止扫描 → **停止采集执行池新任务**（已有任务跑完）→ 排空治理队列（**上限 60s**）→ 排空情感队列（上限 30s）→ **剩余消息保留 `parse_status=0`，由启动补偿任务接管**（因 P-02 的补偿机制已建立，超时不再等于丢数据）；
- 新增指标 `shutdown_drained` / `shutdown_pending_leftover`。

## C-07（P1）单机单实例下的演进接口预留

> 来源：汇报版评审 §三.1 / §三.5 / §六方案四。
> **立场**：V1 单机单实例是正确取舍（≤100 用户、50 并发），**不引入任何分布式组件**；
> 但必须把"未来拆分的接缝"在 V1 就用接口表达出来，否则 V2 就是重构而非扩展。

### 六条必须抽象的接缝（只定义接口，V1 用进程内实现）

| # | 接缝 | V1 实现 | V2/V4 替换目标 | 约束 |
|:-:|---|---|---|---|
| 1 | **任务异步接口** `PipelineQueue` | `LinkedBlockingQueue` 进程内 | Redis Stream / MQ | 只暴露 `offer(msg)` / `poll()` / `水位()`，禁止业务代码直接操作具体队列类型 |
| 2 | **推送协议** `PushGateway` | 内存 `SimpMessagingTemplate` | Redis Pub/Sub 广播 | 消息体结构与 04 §8 完全对齐；`channel:user:{userId}` 键已预留，V1 直接写实现 |
| 3 | **配置中心接口** `ConfigProvider` | DB + Redis 热加载 | Nacos / Apollo | 所有业务参数（词典、阈值、源策略）**只能**经此接口读取，禁止 `@Value` 直读 yml |
| 4 | **规则引擎抽象** `RuleEvaluator` | 白名单指标 + switch | DSL 表达式树 | V1 的 `evaluate(metric, op, value)` 签名即 V2 DSL 的叶子节点，保持签名不变 |
| 5 | **回放服务接口** `ReplayService` | 本进程内同步执行 | 独立 Worker 进程 | 入参 `(sourceCode, start, end, target)` 与 04 §4 契约一致；返回 `taskId` 而非结果 |
| 6 | **事件总线入口** `DomainEventPublisher` | Spring `ApplicationEvent` | 消息队列 | 领域事件（文档入湖、情感完成、指数重算、告警触发）统一经此发布，订阅方不直接调用生产方 |

### 落地的三条硬性约束（写入 05 §5 各模块）

1. **跨模块调用只能走接口，不能走具体类**：采集层不得直接持有治理 Worker 引用，只能 `pipelineQueue.offer()`；
2. **禁止在业务代码中出现 `RedisTemplate` / `StringRedisTemplate`**：统一封装到 `CacheService`（键规范见 02 §四），为将来换实现留口；
3. **领域事件的 payload 必须是自洽 DTO**（含 `biz_id`、时间戳、版本号），不能传实体对象——否则 V4 序列化时会踩坑。

### 明确不做（避免 V1 过度设计）

- 不做服务拆分、不引入 MQ、不做注册中心、不做配置中心中间件（与 `01 §四` Won't 项一致）；
- 不做分布式锁（V1 用 `sourceLocks` 进程内 `AtomicBoolean`，V4 再换 Redisson）；
- **不为了"将来可能"提前写多实例代码**——只保证接口形状正确。

## C-06（P1）缓存雪崩与热点防护

> 来源：汇报版评审 §五"缓存热点与失效抖动"。

### 问题

`02 §四` 的 Redis Key 表只定义了 TTL，**没有防雪崩设计**：

| 风险点 | 现状 | 后果 |
|---|---|---|
| 固定 TTL | `quote:snapshot:{code}` 10s、`sentiment:latest:{code}` 24h | 盘中数千标的**同刻批量过期** → 回源打爆 MySQL |
| 无空值缓存 | 情绪指数 NULL 不写缓存 | 冷门股/新股被高频穿透查询 |
| 热点 key | 茅台/宁德等热门股 + 词典 Trie | 单 key 热读，Redis 单分片打满 |
| 缓存故障 | 06 §6 演练 2 只说"降级回源 MySQL" | 无回源限流，Redis 挂掉瞬间 DB 被打穿（演练要求"无 5xx 雪崩"实际不可达） |

### 修正

**1）TTL 加抖动**（所有 Key 一律 `基础TTL + random(0, 20%)`）

| Key | 原 TTL | 修订 |
|---|---|---|
| `quote:snapshot:{code}` | 10s | 10s + rand(0,2s) |
| `sentiment:latest:{code}` | 24h | 24h + rand(0,2h) |
| `watchlist:{userId}` | 30min | 30min + rand(0,5min) |
| `sentiment:wordcloud:{code}` | 30min | 30min + rand(0,5min) |

**2）空值缓存**：情绪指数为 NULL 时写哨兵值 `"__NULL__"`，TTL **缩短至 5min**（避免长期屏蔽真实数据），查询侧识别哨兵直接返回 null，不回源。

**3）热点本地缓存**：Caffeine 本地缓存（容量 1000，TTL 3s）只缓存 `quote:snapshot` 与 `sentiment:latest` 的 **Top 200 热读标的**（按访问计数淘汰），降低 Redis 单 key 压力。

**4）缓存故障时的回源限流**（这是"演练 2 无雪崩"能否成立的关键）

```
Redis 不可用 → 开启"降级模式"开关（全局 AtomicBoolean，10s 探测一次恢复）
   → 回源查询走信号量限流（并发 ≤ 20）
   → 超出限流：详情页/workbench 直接返回缓存缺失字段为 null，不报错、不回源
   → 指标 cache_fallback_active / cache_fallback_rejected_total
```

**修订落点**：`02 §四` Redis Key 表增加"抖动"列；`05 §5.6` 前端约束补充"降级模式下允许字段缺失"；`06 §6` 演练 2 的验收改为"无 5xx，且 DB QPS 峰值 ≤ 基线×3"。

## C-09（P2）全局追踪标识约定

> 来源：汇报版评审 §五"任务幂等复杂：统一任务 ID 与事件 ID"。

当前 `task_id` / `doc_id` / `dedup_key` / `trace_id` 四套标识各自为政，跨环节排障要人肉拼。约定如下（写入 `06 §5` 日志规范）：

| 标识 | 生成方 | 生命周期 | 用途 |
|---|---|---|---|
| `biz_id`（UUID36） | **采集任务创建时**生成一次 | 贯穿采集 → 治理 → 情感 → 指数 → 告警 | 全链路串联；MDC 注入；日志必带 |
| `trace_id` | HTTP 请求入口 | 单次 API 调用 | API 响应体返回；**WS 消息同样携带**（见 API-07） |
| `task_id` | 采集任务 | 单任务 | 记账与重放溯源（`replay_of` 指向它） |
| `doc_id` | 治理落库 | 文档级 | 幂等锚点，**禁止 REPLACE 变更** |
| `dedup_key` | 告警 | 去重窗口 | 告警合并锚点 |

**约束**：
1. `biz_id` 随消息体在队列间传递（治理/情感队列的 DTO 必带），不得在下游重新生成；
2. `m3_task_instance.biz_id`、`sys_audit_log.biz_id`、日志 MDC 三处同源；
3. 告警事件 `event_data` 中记录**触发它的 `biz_id`**，实现"这条告警是哪批采集数据算出来的"端到端可解释（直接支撑汇报版"可追溯"要求）。
