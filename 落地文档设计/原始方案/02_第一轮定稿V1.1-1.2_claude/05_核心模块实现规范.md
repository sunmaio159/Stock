## 5.1 采集调度器

### 设计要点（修正）
1. **扫描与执行分离**：单线程 `scheduleAtFixedRate(30s)` 只做扫描分发；任务执行用独立 `ThreadPoolExecutor(8, CallerRunsPolicy)`——原伪代码共用调度池，长任务会饿死调度（勘误 E1）。
2. **限流真实发放**：每源一个 Guava `RateLimiter`（`create(qps)`，`acquire()` 阻塞获取），删除原伪代码中只 `get` 不 `incr` 的无效 Redis 限流段（勘误 E2，P0）。
3. **游标 DB 为准**：`m3_source_config.last_cursor` 唯一事实源；任务启动读入内存，**整批处理成功后才更新 DB**；Redis 只做读缓存（勘误 E3，P0）。
4. **三态熔断**：状态与 `circuit_open_until` 存 `m3_source_config`；半开=放行 1 个探测请求，失败则指数退避重开路（30s→2min→10min→30min）；403/验证码特征立即开路+P0 告警（勘误 E4）。
5. 记账：每任务一行 `m3_task_instance`（含 record_count/duration/error），部分失败记 `status=3`。

### 关键骨架

```java
@Component
public class CrawlScheduler {
    private final ThreadPoolTaskScheduler scanner;   // poolSize=1, 仅扫描
    private final ThreadPoolExecutor execPool;       // 8线程 CallerRunsPolicy
    private final Map<String, AtomicBoolean> sourceLocks = new ConcurrentHashMap<>();
    private final Map<String, RateLimiter> limiters = new ConcurrentHashMap<>();

    void scanAndDispatch() {
        if (!running.get()) return;
        for (SourceConfig src : sourceConfigService.selectDue(LocalDateTime.now())) {
            AtomicBoolean lock = sourceLocks.computeIfAbsent(src.getSourceCode(), k -> new AtomicBoolean());
            if (!lock.compareAndSet(false, true)) continue;
            try {
                execPool.submit(() -> { try { executeWithGuard(src); } finally { lock.set(false); } });
            } catch (RejectedExecutionException e) {
                lock.set(false);  // CallerRunsPolicy下不抛,防御性处理
                Metrics.counter("crawl_task_skipped", "source", src.getSourceCode()).increment();
            }
        }
    }

    void executeWithGuard(SourceConfig src) {
        if (!circuitBreaker.allow(src)) { Metrics.counter("crawl_circuit_skip", ...); return; }
        TaskInstance run = taskService.start(src);          // status=RUNNING, 读入last_cursor
        try {
            RateLimiter limiter = limiters.computeIfAbsent(src.getSourceCode(),
                k -> RateLimiter.create(src.getRateLimitQps()));
            CrawlResult result = adapterRegistry.get(src).fetch(src, limiter);  // 内部acquire()
            rawRecordService.batchUpsert(result.records(), run.getId());        // 幂等upsert
            var docs = adapter.parse(result.records());
            driftDetector.check(src, docs);                  // P1→阻断+告警; P2/P3→记m3_drift_log
            governancePipeline.submit(docs);                 // 投治理队列
            sourceConfigService.commitCursor(src.getSourceCode(), result.newCursor()); // 成功后提交
            circuitBreaker.onSuccess(src);
            taskService.finish(run, "SUCCESS", result.recordCount(), null);
        } catch (AntiCrawlException e) {                     // 403/验证码特征
            circuitBreaker.openImmediately(src); alertService.p0("源被反爬: " + src.getSourceCode());
            taskService.finish(run, "FAILED", 0, e.getMessage());
        } catch (Exception e) {
            circuitBreaker.onFailure(src);
            taskService.finish(run, "FAILED", 0, e.getMessage());
        }
    }
}
```

## 5.2 治理流水线

### 设计要点（修正）
1. **队列分段**：`governQueue(LinkedBlockingQueue, 10000)` + 4 消费线程；队列满→**offer 失败即告警并让上游阻塞等待重试**（背压），禁止原伪代码的"队列满就同步直接处理"（那会让采集线程承担治理耗时，且绕开限流）。
2. **单条事务**：去掉批级 `@Transactional`（原 P0 缺陷：批内一条异常→rollback-only→整批回滚）。`persistDoc` 单条 `@Transactional`；单条失败重试 3 次（退避 1/2/4s）→ `m4_dead_letter`，继续处理后续。
3. **情感分析移出治理事务**：persist 成功后投 `sentimentQueue` 异步处理。
4. Clean：Jsoup `Safelist.none()`；广告词正则从 `m5_sentiment_dict(type=6)` 加载（热更新）；繁简用 opencc4j；正文截断 **5000**（原代码 2000，与文档 5000 矛盾，取 5000）。
5. Dedup：SimHash64（标题+正文，中文二元组分词 + murmur3_128）；Redis 索引 `simhash:bucket:{code}:{高16位}` 分桶，桶内比对汉明 ≤3；桶数量上限按时间淘汰最旧桶；**禁止溢出整删**（原实现整删导致窗口去重瞬间失效）。
6. Entity：AC 自动机词典 = `m2_security.security_name` + `m2_security_alias`；热更新用**双 buffer**（构建新 Trie 后原子切换引用）；主标的 = 提及次数最多实体，全部实体写 `m4_entity_mention`。
7. Quality：扣分制——内容 <10 字 -2 分、命中广告词 -3、作者 24h >50 帖 -2（key=`source:authorId`，incr+首次 setnx 带 TTL）、重复 -2，高互动 +1，clamp [1,5]。

## 5.3 情感引擎与情绪指数

### 5.3.1 L1 规则引擎（修正）

1. **词典 100% 来自 `m5_sentiment_dict`**，删除全部硬编码词表（原硬编码中 `Map.ofEntries` "大幅"重复、`Set.of` "不"重复，**启动即崩**——P0）。
2. 分词：词典内词用 AC 自动机最长匹配（情感词/否定词/程度副词/转折词同一 Trie），其余逐字跳过。
3. 否定与程度窗口：情感词向前看 **3 个已切分 token**（原"前2个"且分词不可靠导致漏判）。
4. 转折规则：命中转折词后置 `inTransition=true`，**遇句读符号（。！？；\n）复位**（原实现一旦置位传染到文末）。
5. 输出：`score = tanh(ΣfinalScore / 3)`；label 阈值 ±0.15；`confidence = min(1, |score|×2 + 命中数×0.1)`；`detail` 记录命中词与翻转明细（可解释性）。
6. 热加载：词典版本号存 Redis，变更后新版本全量重建 Trie 原子切换。

### 5.3.2 BudgetRouter（V1）

V1 恒路由 L1，但**如实记录**：`requested_level`（路由决策）与 `engine_level`（实际执行）分列——原伪代码把降级后的结果标成 L3，污染数据（影响未来 L2 训练集质量）。

### 5.3.3 情绪指数（修正）

```
Si = 50 + 50 × Σ(wk × score_k)/Σ(wk)     # 量纲 [0,100]，中性 50
w_time = 0.5^(Δt/24h)，Δt = 帖发布时间 → 交易日收盘时刻   # 非 now()！
无数据日：sentiment_index = NULL, post_count = 0          # 不是 0 不是 50
```

- 日频任务：交易日 17:00（过 `m2_trade_calendar` 判断，非 `MON-FRI` cron）；UPSERT `uk_scope_date`；板块指数 = 成分股按帖量加权，scope_type=INDUSTRY。
- 15min 滚动：交易日 9:00-15:30 每 15min，仅处理该窗口有新帖的标的；写 `m5_sentiment_index_15m` + 刷 `sentiment:latest:{code}`。
- 重放联动：API10 重放完成 → 产出受影响 (code, tradeDate) 清单 → 重算指数 → 刷缓存。

### 5.3.4 突增检测

| 模型 | 规则 | 版本 |
|---|---|---|
| 环比突增 | 当日累计 > **上一交易日**同期 ×3 且绝对值 >30（必须走交易日历取"上一交易日"，原 `minusDays(1)` 周一必误报） | V1 |

## 5.4 投研分析（V1 边界 + V3 目标）

**V1**：详情页聚合 = 七卡片 `CompletableFuture` 并行（每卡超时 500ms，超时/异常 → `{available:false}`）；仅 overview/sentiment/risk(部分) 有真实数据。
**V3 评分卡（锁定设计，届时实现）**：
- 权重唯一来源 `ana_factor_def`（删除代码常量——原 §3.4.1 硬编码与 §3.4.2 表化自相矛盾）
- 真 z-score：行业维度内 (x-μ)/σ → 50+15z；行业样本 <10 用全市场兜底；无数据维度给 NULL 且综合分按剩余维度权重重归一（**禁止静默填 50**——新股/冷门股得分会被系统性拉向中位，需在 UI 标"数据不足"）
- 表达式求值用 Aviator（删除原 switch 中引用未定义变量的 default 分支——编译错误级）
- 快照：每日 17:30 对**全部有评分标的**（非仅"已评过分的"）写 `ana_stock_score_history`；保存 `factor_def_version` 支持口径回溯

## 5.5 告警引擎（V1 基础版 + V2 DSL）

### V1 实现范围
- 规则评估循环：每 30s 扫描启用规则 → 按 scope 展开标的 → 求值白名单指标（04 §7）→ 降噪 → 落 `m8_alert_event` → 推送
- **priority 显式存储**于规则（删除原"按规则名称猜优先级"的实现——`rule.getName().contains("异动")` 极其脆弱）
- 降噪三件套（全部 Redis 原子操作）：
  1. 冷却：`alert:cooldown:{rule}:{code}` SETNX TTL=cooldown
  2. 日上限：`alert:daily:{rule}:{code}:{date}` incr（首次 setnx 2d TTL），超限 suppress
  3. 合并：`dedup_key = rule+code+type+窗口起点` 唯一索引兜底；命中则 `merge_count+1` 不新推
- 夜间勿扰：`quiet_hours` 时段内仅 priority ≤ minPriority 放行，其余**缓存到 08:00 补发**（非丢弃）
- 渠道：V1 仅 `in_app`（WS + 工作台待办）+ `wecom`（群机器人 markdown，webhook 加密存 `m8_alert_channel`）；发送失败 `push_status=2` 重试 3 次，仍败告警运营

### V2 目标
DSL 条件树（and/or 嵌套）、表单可视化编辑器、规则回测 API、dingtalk/email 渠道。
