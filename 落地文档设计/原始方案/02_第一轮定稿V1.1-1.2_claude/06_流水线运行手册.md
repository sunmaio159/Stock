# 06 流水线运行手册（定稿）

> 面向运维与值班：线程模型、异常矩阵、监控指标、故障演练、备份与合规。

## 1. 线程与队列全景

```
scan线程(1) ──分发──> crawlExecPool(8, CallerRuns) ──upsert──> MySQL
                              │ 投递
                              ▼
                    governQueue(10000) → governPool(4) ──单条事务──> MySQL
                              │ 合格(quality≥2 且非重复)
                              ▼
                    sentimentQueue(10000) → sentimentPool(2) → L1引擎(纯CPU)
                              │
                              ▼
                    派生调度: 15min滚动 / 日频17:00 / 突增检测(V1环比)
                              │
                              ▼
                    alertEvalPool(2, 30s周期) → 降噪 → 推送池(2)
```

队列满策略：上游阻塞重试 + `pipeline_queue_full` 告警；**禁止**丢弃或转同步直处理。
优雅停机：收到 SIGTERM → 停止扫描 → 队列排空（≤30s）→ 落盘未完成游标。

## 2. 异常处理矩阵

| 异常 | 检测 | 处理 | 恢复 |
|---|---|---|---|
| HTTP 超时/5xx | HttpClient | 重试 ≤3（退避 1/2/4s），记失败 | 连续 5 次任务失败→熔断开路 |
| 403/验证码特征 | 响应特征匹配 | 立即开路 + P0 企微告警运营 | 运营更新 UA/Cookie → 手动半开 |
| 解析异常 | Adapter.parse | RawRecord `parse_status=2`，任务记部分成功 | 修 Adapter → API 重放 |
| P1 字段漂移 | SchemaValidator | 阻断该批 + `m3_drift_log` + 告警 | 修复 → 重放 30 天 Raw Lake |
| DB 写失败 | SQLException | 重试 3 次 → 本地磁盘 buffer 文件 | DB 恢复后启动扫描 buffer 回放 |
| 治理单条失败 | Worker catch | 重试 3 次 → `m4_dead_letter` | 死信重试任务（每小时） |
| 推送失败 | 渠道非 2xx | 重试 3 次，`push_status=2` | 渠道恢复后补偿推送 |

## 3. 幂等链（三级）

`m3_raw_record.uk(source,outer,fetched_day)` → `m4_normalized_doc.uk(source,outer)` → `m5_sentiment_result.uk(doc,engine)`。
结论：任意环节重试/重放不产生重复业务数据；重放以 UPSERT 覆盖治理与情感产物。

## 4. 对账（每日 02:00）

```
采集入库数 = 治理产出 + 去重标记 + 无实体丢弃 + 死信
差异率 > 0.1% → 告警 + 自动生成差异报告（按源/按阶段分解）
```

## 5. 监控指标（Micrometer，Actuator 暴露）

| 指标 | 标签 | 告警阈值 |
|---|---|---|
| `crawl_task_total` | source,status | 单源 1h 成功率 <99% |
| `crawl_task_duration` | source | P95 > 基线×2 |
| `crawl_circuit_state` | source | 开路 >5min |
| `crawl_zero_new_hours` | source | 连续 >2h（反爬/改版信号） |
| `pipeline_queue_size` | queue | >8000 持续 10min |
| `govern_dead_letter_total` | stage | 1h 增量 >100 |
| `sentiment_index_lag` | — | 交易日 18:00 未完成 |
| `alert_push_fail_total` | channel | 1h >5 |
| `reconcile_diff_ratio` | layer | >0.1% |
| `api_latency` | uri | 详情页 P95 >800ms |

日志规范：全链路 traceId 透传（采集→治理→情感→告警同一 traceId，MDC 注入）；WARN+ 必带 `sourceCode`/`securityCode`。

## 6. 故障演练清单（上线前必过）

| # | 注入 | 预期 | 验收 |
|:-:|---|---|---|
| 1 | 东财源返回 403 | 立即开路 + P0 告警；雪球/同花顺照常 | 告警 ≤1min 到企微 |
| 2 | kill Redis | 详情页/工作台降级回源 MySQL（P95 允许升至 2s）+ 告警 | 无 5xx 雪崩 |
| 3 | kill MySQL 30s | 采集落磁盘 buffer，恢复后自动回放 | 对账 diff=0 |
| 4 | 治理队列灌满 | 背压 + 告警，不丢消息不 OOM | 恢复后自动消化 |
| 5 | 企微 webhook 失效 | push_status=2，站内信兜底 | 事件不丢 |

## 7. 备份策略（新增，评审 G1）

| 对象 | 方式 | 频率 | 保留 |
|---|---|---|---|
| 核心表（除 m3_raw_record.raw_content） | `mysqldump --single-transaction` | 每日 03:00 | 本地 7 天 + 每周异地 1 份 |
| binlog | 开启，expire 7 天 | 实时 | 7 天（PITR） |
| m3_raw_record | 不单独备份（30 天窗口，重采可补） | — | — |
| Redis | RDB 每日；丢了仅性能降级，可从 DB 重建 | 每日 | 3 天 |

恢复演练：每季度一次"从备份恢复到干净机器"全流程，RTO ≤ 1h。

## 8. 合规清单（新增，评审 G2）

1. 帖文展示：摘录 ≤200 字 + `originUrl` 跳源站；不整篇转载（04 §5 已落地到 API）
2. 作者脱敏：昵称显示首字+***；`author_id` 存 SHA-256，不存源站原始 ID
3. 免责声明：页脚"数据来源于公开渠道，仅供参考，不构成投资建议"
4. 采集自律：遵守 robots.txt；单源 QPS ≤ 5；UA 真实标注；不为绕反爬使用账号池/打码平台
5. 数据处理：用户数据仅自用不二次分发；注销用户 30 天内物理删除其自选/规则数据

## 9. 配置基线（application.yml 关键项）

```yaml
server.timezone: Asia/Shanghai
spring.jackson.time-zone: Asia/Shanghai
aquila:
  crawl:
    exec-pool-size: 8
    circuit: { fail-threshold: 5, open-backoff-seconds: [30, 120, 600, 1800] }
    retry:   { max: 3, backoff-ms: [1000, 2000, 4000] }
  govern:
    queue-capacity: 10000
    simhash: { hamming-threshold: 3, window-hours: 24 }
    content-max-length: 5000
  sentiment:
    l1: { pos-threshold: 0.15, neg-threshold: -0.15 }
    daily-cron: "0 0 17 * * ?"        # 内部再过滤交易日历
    rolling-15m: "交易日 9:00-15:30"
  alert:
    eval-interval-seconds: 30
    default-cooldown-seconds: 900
    default-max-per-day: 10
```

> 业务参数（词典、广告词、源策略、阈值）一律入库 + 热加载；yml 只放工程参数——"调权重不发版"原则。
