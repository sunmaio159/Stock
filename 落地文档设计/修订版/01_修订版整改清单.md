## 二、P0：硬伤（W0 开工前必须关闭）

### P0-01 【已撤回 · 误报 → 重分类为 P2-09】

- **撤回原因**：原判"分区表 UK 不含分区列导致 `ERROR 1659`"不成立。MySQL 规则只要求每个唯一键**包含**分区表达式的**所有列**（约束列的存在性，**不约束顺序**）。经核 02 §四 `m3_raw_record`：`PRIMARY KEY (id, fetched_date)` 与 `UNIQUE KEY uk_source_outer_date (source_code, outer_id, fetched_date)` **均已含 `fetched_date`** → DDL 合法可执行，原 P0 判定作废。
- **保留的建议项（降级为 P2-09）**：W0.2 仍以"31 表 DDL 在 MySQL 8.0.3x 实跑通过"为出口条件（属既有验收项，非缺陷）。详见 §四 P2-09。

### P0-02 收盘价落库链条断裂（Redis TTL 30s vs 收盘任务 15:05）

- **位置**：02 §三数据拓扑 `H1 quote:snapshot:* 30s`；03 链路 2（L63-L71）；04 §1.4（L143-L158）
- **现象**：盘中快照 cron `*/3 * 9-15` + 内部 `isTradingNow()` 判断；A 股 15:00 收盘，`isTradingNow()` 通常在 15:00:00 即返回 false → 最后一帧约写于 14:59:59，TTL 30s 使全部 `quote:snapshot` 键在 **15:00:30 过期**。15:05 收盘任务"Redis 快照 → upsert `m6_quote_daily`"读到空值。03 链路 2 又写"09:25-15:05 每 3s"、04 §3.2 用"收盘时刻"作 Δt 基准 —— 三处收盘时刻口径不一（15:00 / 15:05）。严重度取决于实现者对盘后窗口的解读：最坏 `m6_quote_daily` 全空，最好也是"15:05:00 读 15:05:00 写"的竞态。
- **次生缺陷**：cron 小时域 `9-15` 覆盖 9:00-15:59，与文档声明的 09:25-15:05 不一致（靠内部判断兜底，但配置示例照抄会全天空转 7 小时）。
- **整改方案（收盘定格三段式）**：
  1. 盘中：`quote:snapshot:{code}` TTL 30s（不变，用于 WS/工作台）。
  2. **15:00:00-15:00:20 定格帧**：新增 `quote:close:{code}`，TTL 2h，由 `isCloseTick()`（14:59:55 之后第一次成功拉取）写入；写入前校验 `tradeDate` 与 `close_price` 非空。
  3. **15:05 落库任务改为双通道**：优先读 `quote:close:{code}`；缺失则**当场向健康源直拉一次**（复用 `QUOTE_SNAPSHOT` 路由）；仍失败 → 记 `m4_dead_letter(stage='quote_close')` + P1 告警，**禁止写空值覆盖已有行**。
  - cron 修正：`0/3 0-59 9-14 * * ?` + `0/3 0-5 15 * * ?` 两条，或保留单条并把盘中窗口判断写成显式常量 `QUOTE_ACTIVE_WINDOW=09:25-15:00:20`。
- **验证**：06 新增验收项「15:05 后 `m6_quote_daily` 当日行数 ≥ 标的集数量 × 99%；全源故障演练时旧值不被覆盖」。
- **回写文档**：02 §三热层键清单（增 `quote:close:*`）、03 链路 2、04 §1.4 伪代码。

### P0-03 SimHash 分桶算法不成立（去重召回系统性塌陷）

- **位置**：04 §2「Dedup 分桶」`isDuplicate()`（L193-L205）；02 §三 `H3 simhash:bucket:* 24h`
- **现象**：桶键取 `hash >>> 48`（高 16 位），而命中条件是**全局** 64 位海明距离 ≤3。两篇近似帖只要差异位有 1 个落在高 16 位即分属不同桶，永不比对。近似重复的 3 个翻转位全部落在高 16 位区间的概率约 15%-25%（视近重复强度），**实际召回远低于 06 §3.3 要求的 ≥90%（默认门禁值，见 §〇 U-1）**。
- **次生缺陷**：
  - `security_code` 为 NULL 时桶键退化为 `simhash:bucket:null:*`，所有无主帖挤同一桶，`smembers` 全量返回，Redis 单键热点 + O(N) 反序列化。
  - 桶内元素为字符串化 long，`Long.parseUnsignedLong` 在热路径反复调用。
- **整改方案（分段 LSH + 多桶探测）**：
  ```
  64 位 SimHash 切 4 段 × 16 位 → bandIdx ∈ {0,1,2,3}
  桶键 = simhash:bucket:{securityCode|NA}:{bandIdx}:{bits(bandIdx)}
  查询：4 个桶取并集为候选（候选只需任一段完全相同）→ 再算全局 bitCount ≤3
  依据：海明距离 ≤3 ⇒ 4 段中至少 1 段完全相同（鸽巢原理），召回无损
  ```
  - NULL 标的用 `NA` 占位，并给 `NA` 桶单独设上限（如 5000）与更短窗口（6h），避免热点。
  - 溢出淘汰：按 `bandIdx` 轮转淘汰最旧时间片，禁整桶删除（保留原纪律）。
  - 桶内改存 `long`（Redis Set of numeric string 可保留，但候选比对前置 bloom/长度短路）。
- **验证**：用 500 条人工近重复样本（含 100 组"仅在标题尾部差异"的强干扰对）实测召回，**按 §〇 U-1 执行**：默认门禁值 ≥90%（基线 06 §3.3）；上调至 95% 须以本次实测报告为依据、经 §九 三方评审确认后方可写入 SLA 表。写入 06 §3.3。
- **回写文档**：04 §2 伪代码 + 07 配置基线 `simhash-band: 4, simhash-hamming: 3`；`05_扩展性与演进.md` 无需变更。

## 三、P1：契约与数据模型缺口（所属模块开工前关闭）

### P1-01 Refresh Token / 会话 / 幂等键 无存储落点

- **位置**：03 §三通用约定（AT 2h / RT 7d，RT 旋转，旧 RT 复用 → 吊销全部会话；`Idempotency-Key` 24h 内返回首次结果）
- **现象**：31 表 DDL 无 token/session 表；02 §三 Redis 热层清单只列 `quote:snapshot`/`sentiment:latest`/`simhash:bucket`，**无 RT 与幂等键的位置**。实现时无处存放 → 要么做不出"吊销全部会话"，要么各自发明 key 造成无审计。
- **整改方案（选 Redis，V1 不建表）**：
  - `auth:rt:{userId}:{jti}` → 存 RT 指纹（SHA-256），TTL 7d；刷新时删旧 jti、写新 jti。
  - `auth:rt-used:{jtiHash}` → 命中即判定"旧 RT 复用" → 删 `auth:rt:{userId}:*` 全族 + 写 `sys_audit_log(module='auth', action='revoke_all')`。
  - `idem:{userId}:{key}` → SETNX + TTL 24h，值为首次响应摘要（`code` + 主键 id），重放时从 DB 重组响应。
  - 02 §三热层清单**增补上述三键**及 TTL；03 §三补一句落点说明。
- **验收**：旧 RT 二次使用 → 该用户全部会话失效且审计留痕；同 `Idempotency-Key` 并发 5 次 → 仅 1 次落库。

- **验收**：`granularity=15m` 返回体三字段非契约凭空字段；同版本重算两次一致。

### P1-05 `source_code` 命名与"源粒度"不一致，导致游标/熔断串扰

- **位置**：02 §2.2 能力矩阵（`EASTMONEY`/`XUEQIU`/`THS`/`TENCENT`/`SINA`）vs 02 `m3_source_config` 列注释（`EASTMONEY_GUBA`/`TENCENT_QUOTE`）vs §2.4 示例（`SINA_QUOTE`）
- **现象**：三处命名规则不同。更关键的是 `circuit_state`/`circuit_fail_count`/`last_cursor`/`rate_limit_qps` 都是**单行单列**：东财同时供舆情与行情，若共用一行则**行情熔断会连带封掉股吧采集、两种数据类型的游标互相覆盖**。
- **整改方案**：
  - **明确"一行 = 一个（源 × 数据类型）接入实例"**，命名统一 `{SOURCE}_{DOMAIN}` 大写：`EASTMONEY_GUBA`、`EASTMONEY_QUOTE`、`XUEQIU_GUBA`、`THS_GUBA`、`TENCENT_QUOTE`、`SINA_QUOTE`。
  - 02 §2.2 矩阵增列 `source_code 实例`，把"东财舆情/东财行情"拆成两行展示（能力矩阵保持源视角，另加"实例清单"表）。
  - `adapter_key` 注释清单补齐 `XUEQIU_GUBA`、`THS_GUBA`（当前注释列了 `XUEQIU_STATUS`，与矩阵命名也不一致）。
  - 03 §3.4 采集运营接口的 `sourceCode` 参数示例同步为带域后缀形式。
- **验收**：06 §2.7"单源停用自动切换"演练中，关闭 `EASTMONEY_QUOTE` 不影响 `EASTMONEY_GUBA` 采集与游标。

### P1-06 腾讯/新浪行情不是 JSON，"纯配置零代码"不成立

- **位置**：02 §2.2 矩阵（标注"通用 JSON Adapter（纯配置）"）、§2.3 取值语法（只定义 JSONPath / CSS / regex）、§2.4 示例（突然出现 `csv[3]`）
- **现象**：`qt.gtimg.cn/q=sh600519` 与 `hq.sinajs.cn/list=` 返回 `v_sh600519="1~贵州茅台~600519~1689.50~..."` 波浪分隔文本（GBK），**既不是 JSON 也不是 HTML**。`GENERIC_JSON_LIST` 无法解析；`csv[3]` 语法在文档里未定义，属"示例引用了不存在的规范"。
- **整改方案**：
  - 新增适配器 `GENERIC_DELIMITED`（分隔文本），并正式定义取值语法：`delim[下标]`（如 `delim[3]`）、支持行前缀剥离（`v_{code}="..."`）与 `encoding: GBK`。
  - 02 §2.2 矩阵把腾讯/新浪接入方式改为 `GENERIC_DELIMITED（纯配置）`；§2.3 语法清单增第三类；§2.4 示例改用 `delim[]`。
  - 若坚持 `csv[]` 写法，则在 §2.3 补 `csv[n]` = 按 `,` 切分第 n 项，并明确与 `delim[n]` 的关系（建议只留 `delim[n]`，可配 `delimiter` 参数）。
- **验收**：新增一个行情源（如网易）仅插入 `m3_source_config` 一行即可采集成功，零 Java 变更 —— 这才是"零代码"的真实边界。
